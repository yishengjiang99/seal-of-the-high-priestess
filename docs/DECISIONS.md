Newest last. Each entry gives the decision, why, and what it affects. Scope: docs/SCOPE.md (v2, Oct 6 2026).

## 2026-10-06: App identity reuses the existing ASC record

## 2026-10-06: Native shell = SwiftUI + WKWebView with the game bundled at app://game/
- The engine stays the web game (Canvas 2D at 1280×720), so it has one codebase with the web build. All engine JS ships inside the app (App Review 2.5.2).
- A custom-scheme handler serves the files offline and supports byte ranges for voice clips. Native features (needed for guideline 4.2): native saves with cloud sync and a conflict prompt, suspend save, haptics, game controllers, audio session, settings, and delete-cloud-data.
- iPhone only, landscape only, iOS 17+. The project is generated by XcodeGen in CI (macos-15, Xcode 26).

## 2026-10-06: Saves = native store is the source of truth, server sync with per-slot revisions
- The native `SaveStore` seeds `localStorage` at document start and mirrors every `Platform.setItem`.
- Server: `PUT /v1/saves/:slot` with `If-Match: <revision>`. A stale revision gets 409 plus the server copy. The 10 most recent replaced revisions are kept in history.
- Anonymous identity: installId + secret in the iCloud Keychain (synchronizable), so a new iPhone reaches the same saves. The server stores only hashes.
- **Forward-compatible for IAP:** entitlements will be stored per *player* (the same `players` row that owns the saves), not inside save JSON. A refund or revocation (ASSN v2) then can't be undone by editing or restoring a save. The client reads entitlements from the server and from StoreKit 2 `Transaction.currentEntitlements`, and passes the union to the game as `SOTH_HOST.entitlements`. The game never stores purchase state itself.

## 2026-10-06: Server-driven content = published base + versioned merge-patch overrides
- `GET /high-priestess/api/v1/content` returns ETag/304. Overrides are an RFC 7386 merge patch, validated on the server and again in the client. The game falls back from remote (1.5 s timeout) to the cache to the bundled snapshot. Asset references must be bundled filenames.
- **Forward-compatible for signed bundles (phase 2):** the response is a versioned envelope `{schema, version, baseHash, base?, overrides}`. Phase 2 adds `sig` (Ed25519 over the canonical payload, public key bundled in the app) and new top-level collections `PAYWALL` and `FLAGS`, under the same validator and merge rules. Clients that don't know a collection ignore it. Prices are never part of content; only the offered product ID is.

## 2026-10-07: Phase 2 — IAP (StoreKit 2) with privacy in the same push
- Products (all non-consumable, Family Sharing on): `com.ragnus.weather.fullgame` (USD 4.99), `com.ragnus.weather.fullgame.b` (USD 6.99, price-test variant; either id unlocks), `com.ragnus.weather.supporter` (USD 2.99, cosmetic). No subscriptions, consumables or loot boxes.
- Free = prologue + region 1: maps temple, village, forest and their interiors. Gated = wilderness, meridia, ashen, ruins, throne. Region 1 ends on the `hollow_oak_dead` flag; the forest→wilderness warp is the cliffhanger paywall. Loading a save that sits in a gated map also asks (refunded / new device without restore).
- **The web build never gates** (`Platform.gate` only acts when `Platform.native`). The paywall is iOS-only.
- Entitlement = union of StoreKit 2 verified `Transaction.currentEntitlements` on the device and the server's per-player entitlements. `appAccountToken` = the player ID (UUID). The last known entitlements are cached in UserDefaults and injected as `SOTH_HOST.entitlements`, so gating is correct before StoreKit answers.
- Server verification: the client uploads `jwsRepresentation`. The server verifies the x5c chain up to the pinned **Apple Root CA G3** (SHA-256 63343abf…3e9179), Apple's leaf/intermediate marker OIDs and the ES256 signature, then stores the signed transaction with the player. ASSN v2 (`POST /v1/iap/notifications`, production + sandbox): REFUND/REVOKE revokes, REFUND_REVERSED restores; deduplicated by notificationUUID.
- **Deviation:** the App Store Server API lookup (authoritative refetch) is implemented but **off**. It needs an *In-App Purchase* key (issuer + key ID + .p8), which isn't the ASC API key we have. Set `ASSA_KEY_ID`, `ASSA_ISSUER_ID`, `ASSA_P8` in /etc/temple.env to switch it on. Until then, verification relies on the JWS chain, which is cryptographically sufficient. Flag for the Chief of Staff.
- Paywall: full-screen SwiftUI sheet. Copy, art, placements, the offered Full Game product id and the A/B split all come from server content (`PAYWALL`). **The price is always StoreKit's `displayPrice`**, and the validator rejects any `price` key in PAYWALL. Price-test bucket = FNV-1a(installId) over `offerVariants` weights, which is stable per install. Restore Purchases is on the paywall and in Settings; Terms/Privacy links are on the paywall.
- Supporter Pack (cosmetic only): Voice Gallery (replay bundled voice lines), an alternate app icon "Kael, unchained" (`AppIconKael`), and a supporter badge in Settings. **Deviation from "alternate portraits":** no alternate portrait art exists, so the alternate icon + gallery replace it.
- Funnel: first-party only (`paywall_shown`, `purchase`, `restore`, `region_complete`) to `POST /v1/events` on our server. They're batched and persisted until sent, `FLAGS.funnelEvents=false` switches them off, and the server deletes events after 13 months. Funnel events and transaction uploads use the device identity even when cloud save is off (needed for entitlements; disclosed).
- Privacy (same push): the privacy page adds Purchase History + Product Interaction; terms add an IAP section; support adds restore/refund FAQ; PrivacyInfo adds PurchaseHistory (App Functionality) + ProductInteraction (Analytics), all linked to the player ID, no tracking. The ASC questionnaire answers are in docs/asc/app-privacy.md (to be entered by Yisheng with the rest of the App Privacy section). Delete cloud data now also deletes entitlements + events; purchases come back with Restore.
- **Deviation:** offer codes and the launch promo are deferred. Offer codes need the IAPs to exist and be approved in ASC first; the launch promo is a pricing decision for Yisheng. Nothing in the client blocks them (StoreKit 2 redemption sheet can be added with one call).
- Local testing: `ios/StoreKit/Products.storekit` (scheme run action + SKTestSession unit test with purchase + refund). The App Review IAP screenshot comes from the simulator run with `-paywallDemo` (shows the paywall with the USD tier as a placeholder price when StoreKit has no products).

## 2026-10-07: Phase 2 — signed server-driven content bundles
- Schema 2 envelope `{schema:2, kid, alg:"Ed25519", payload:"<json string>", sig}`. The signature covers the exact payload string (no canonicalization ambiguity). The payload carries `have` (the client's bundled hash) so a cached base can't cross app builds. The server signs at response time with `CONTENT_SIGNING_KEY` (PKCS#8, generated on the droplet, never leaves it). Public keys: `js/content-keys.js` + `ContentKeys.swift` (a test checks they match) and `GET /v1/content/keys`. Schema 1 (unsigned) stays for build 1.
- iOS verifies natively: the page fetches `app://game/__content`, the shell fetches the server, verifies with CryptoKit, caches the last good envelope in Application Support (re-verified on read), and the page trusts it (`contentVerified`). The web build verifies with WebCrypto Ed25519 and re-verifies its localStorage cache on every load. Anything unverifiable falls back to the bundled snapshot.
- New collections: `PAYWALL` (copy/art/placements/offer/variants/gated maps, no prices) and `FLAGS` (primitive feature switches: `paywall`, `supporterPack`, `voiceGallery`, `funnelEvents`). The validator reverts a bad PAYWALL to the bundled one (it must never gate `temple`, may only reference known products/maps).
- Admin: `server/cli/temple-content.mjs` (status, history, pull, push, set/unset, flag, offer, offer-split, rollback, verify). It reads the admin token from env or over ssh and never prints it. Publishing a new base is still CI (`content-publish`) on push to main.
- Threat model: transit/cache tampering and a compromised CDN/proxy. A compromised droplet can sign anything, but content is data only (App Review 2.5.2), so the worst case is wrong text or numbers, never code.

## 2026-10-07: Chief of Staff decisions (A–D)
- **(A) Price test** between `fullgame` ($4.99) and `fullgame.b` ($6.99), 50/50, with **no intro discount**.
  - Config: `PAYWALL.offerVariants` 500/500, plus a kill switch `FLAGS.priceTest`. Both are server content (`temple-content offer-split …`, `temple-content flag priceTest false`).
  - The arm is an FNV-1a hash of the **player ID** (install ID only before the first server contact). It's remembered on the device per split, so a player never changes arm unless the split itself changes.
  - `paywall_shown` and `purchase` events carry `product`, `variant`, `env`, and for purchases the StoreKit `price` + `currency`. Admin metrics (`/v1/admin/metrics` → `priceTest`) compute views, verified purchases, refunds and revenue per arm from the signed transactions' `price`, and report USD revenue per paywall view. Production only by default; `?env=all` includes sandbox.
  - **Decision rule:** the winner is the arm with the higher USD revenue per paywall view, called once total production paywall views reach **300** or **3 weeks** after the first view, whichever comes first. Then set `offer` to the winner and clear `offerVariants`.
  - **Reviewer path:** any non-production install (TestFlight and App Review use sandbox receipts; Xcode and simulator builds too) always gets `fullgame` ($4.99), no matter the split. The review notes say so.
